# MARKCHAT — PERMANENT ANTIGRAVITY PROJECT RULES

These instructions are mandatory for every task performed in this
repository. They take precedence over convenience, assumptions,
generic AI coding habits, and unsolicited redesign decisions.

============================================================
1. PROJECT IDENTITY AND PURPOSE
============================================================

The project is the MARKCHAT MARKETING WEBSITE.

MarkChat is a commercial customer communication and engagement
platform aimed at businesses, including businesses in Kenya.

The website must communicate the actual MarkChat product,
its verified functionality, its value, and its intended users.

MarkChat is NOT an open-source product.

The underlying project is based on Chatwoot Community Edition.
Do not represent Chatwoot Enterprise functionality as MarkChat
functionality unless it has been independently implemented
and verified in this repository.

Never confuse the marketing website with the actual application.

============================================================
2. PRESERVE THE EXISTING PROJECT — NO REBUILD
============================================================

The existing website is based on the Virex Astro Enterprise
template, deliberately selected by the project owner.

You MUST improve the existing implementation.

You MUST NOT:
- Replace the website with a new template.
- Rebuild the project from scratch.
- Replace Astro with another framework.
- Replace Tailwind CSS with another styling framework.
- Delete and recreate existing pages without justification.
- Introduce a new design system unnecessarily.
- Remove working functionality merely to simplify development.
- Change the project's architecture without a demonstrated need.
- Replace existing components with generic alternatives.

Before changing anything, inspect the existing implementation.

Reuse existing components, utilities, layouts, configuration,
design tokens, and established development conventions wherever
practical.

============================================================
3. STRICT VISUAL IDENTITY PRESERVATION
============================================================

The existing Virex design identity is the foundation.

Preserve the existing:
- Font families and typography system.
- Font sizes and heading hierarchy.
- Font weights and text treatments.
- Spacing scale and layout proportions.
- Border radii and component shapes.
- Colour tokens and visual relationships.
- Light and dark themes.
- Navigation conventions.
- Buttons, cards, forms, and interaction patterns.
- Responsive breakpoints and behaviour.
- Animation conventions and transition styles.
- Component architecture and visual consistency.

Do not introduce arbitrary fonts, colours, gradients,
shadows, spacing systems, or visual styles.

Do not make the website look like an unrelated SaaS template.

Improve the quality, hierarchy, clarity, and consistency
without destroying the existing visual identity.

Any proposed visual change must be justified by a clear
improvement to usability, readability, or presentation.

============================================================
4. PRODUCT TRUTH — NO INVENTED FEATURES
============================================================

This is a critical rule.

Never invent, assume, exaggerate, or advertise functionality
that has not been verified.

Before writing or modifying product claims:

1. Inspect the relevant implementation.
2. Inspect available configuration and integrations.
3. Inspect existing documentation.
4. Determine what actually works.
5. Distinguish implemented functionality from planned work.
6. Write marketing content only within verified boundaries.

Never assume that a feature exists simply because:
- Chatwoot supports it.
- A competing platform supports it.
- A template contains a section for it.
- A package or dependency is installed.
- An integration logo exists.
- A configuration variable has been declared.
- A feature appears in a roadmap or comment.

Do not advertise planned, incomplete, experimental, or
unverified functionality as currently available.

Where functionality cannot be verified, omit the claim
or explicitly label it as planned only when authorised.

============================================================
5. STRICT MARKETING CLAIMS
============================================================

Never fabricate:
- Customer numbers.
- Active users or businesses.
- Testimonials.
- Customer logos or partnerships.
- Case studies.
- Conversion statistics.
- Revenue improvements.
- Delivery rates.
- Uptime percentages.
- Performance guarantees.
- Security certifications.
- Compliance certifications.
- Pricing and discounts.
- Free trials or promotional credits.
- Support availability.
- Service-level agreements.
- Integration capabilities.

Do not use fabricated claims such as:
- 100% fraud elimination.
- Guaranteed message delivery.
- Zero risk of WhatsApp bans.
- Unlimited agents.
- 99.9% uptime.
- SOC 2 certified.
- 24/7 support.
- Guaranteed revenue growth.

These claims are prohibited unless supported by reliable,
specific evidence and authorised for publication.

Do not create fictional testimonials or present sample
businesses as actual customers.

Do not invent a customer count to make the website appear
more established.

============================================================
6. MARKCHAT PRODUCT POSITIONING
============================================================

Communicate MarkChat as a customer communication and
engagement platform.

Potential product areas include:
- Omnichannel customer conversations.
- WhatsApp communication.
- SMS communication.
- Customer engagement.
- Team inbox and conversation management.
- M-Pesa-related payment workflows.
- AI-assisted customer interactions.

However, every individual capability must be verified
against the actual implementation before publication.

Never imply that every communication channel, payment
method, automation, or AI capability is available by default.

Do not imply that MarkChat owns or operates third-party
infrastructure when it actually relies on an external provider.

Explain third-party dependencies accurately where relevant.

============================================================
7. WEBSITE CONTENT QUALITY
============================================================

The website must be professionally written, informative,
credible, and commercially persuasive.

Avoid:
- Generic AI-generated marketing language.
- Repeated slogans across different sections.
- Empty statements about revolutionising businesses.
- Unsubstantiated superlatives.
- Repetitive feature descriptions.
- Filler paragraphs.
- Unnecessary technical jargon.
- Fake urgency and fabricated scarcity.

Every page must have a clear purpose.

Every section must communicate useful information.

Content must explain:
- What the product does.
- How the functionality works.
- Who benefits from it.
- What problem it solves.
- How customers use it.
- What is required to use it.
- Any relevant limitations or dependencies.

Write naturally and professionally for the intended audience,
including Kenyan businesses where appropriate.

============================================================
8. VISUAL PRODUCT SHOWCASES
============================================================

Visual presentation is a major project requirement.

Do not create a website consisting primarily of text,
generic feature cards, and decorative gradients.

Use meaningful visual demonstrations, including:
- Product interface screenshots.
- Accurate interface mockups.
- Conversation examples.
- Customer communication workflows.
- Payment workflow illustrations.
- Channel diagrams.
- Product walkthroughs.
- Comparison visuals.
- Carefully designed feature demonstrations.

Use actual MarkChat screenshots whenever available.

If screenshots are unavailable, create accurate mockups
based only on verified functionality.

Never fabricate interface controls or workflows that
suggest unsupported product capabilities.

Do not use unrelated stock photography as a substitute
for genuine product demonstrations.

============================================================
9. NAVIGATION AND INFORMATION ARCHITECTURE
============================================================

All navigation must be intentional and functional.

Check:
- Main navigation.
- Dropdowns and mega menus.
- Footer navigation.
- Product navigation.
- Integration navigation.
- Resource navigation.
- Calls to action.
- Internal links.
- Login and registration destinations.

Never create dead links.

Never advertise a page or product section that does not
exist or has no meaningful content.

Mega menus, where appropriate, must be useful, organised,
visually consistent, responsive, and accessible.

Do not introduce complicated navigation merely for decoration.

============================================================
10. INTEGRATIONS AND THIRD-PARTY SERVICES
============================================================

Verify every integration before advertising it.

For each integration establish:
- Whether it is implemented.
- Whether it is operational.
- Whether it requires customer configuration.
- Whether it requires third-party credentials.
- Whether it has limitations.
- Whether the advertised workflow is supported.

Never display an integration logo as proof of a working
integration.

Do not imply official partnerships or endorsements
without evidence.

Do not claim that a third-party service is directly
controlled or owned by MarkChat.

============================================================
11. PRICING AND COMMERCIAL INFORMATION
============================================================

Never invent prices, subscription plans, discounts,
billing arrangements, free trials, or usage allowances.

Inspect the existing commercial configuration and
authorised project information.

Where pricing is not confirmed, do not manufacture
commercial figures.

Clearly distinguish included functionality from
paid third-party services or usage-based charges
where that information is verified.

============================================================
12. TECHNICAL IMPLEMENTATION RULES
============================================================

Preserve the established technical stack.

Current project baseline includes:
- Astro.
- Tailwind CSS 4.
- Astro MDX.
- Astro Icon.
- Existing project components and utilities.

Inspect package.json and actual source files before
assuming the current implementation.

Use existing conventions and dependencies first.

Do not install additional packages unnecessarily.

Do not duplicate components that already exist.

Do not introduce unnecessary client-side JavaScript.

Keep components maintainable and appropriately reusable.

Preserve SEO metadata, accessibility, semantic HTML,
responsive behaviour, and performance.

Do not expose API keys, secrets, tokens, or environment
variables in client-side code or public website content.

Do not modify environment files without explicit need
and authorisation.

============================================================
13. RESPONSIVE DESIGN AND ACCESSIBILITY
============================================================

Every improvement must work across:
- Desktop.
- Laptop.
- Tablet.
- Mobile.

Check navigation, menus, typography, images, cards,
tables, forms, and calls to action at different widths.

Maintain accessible colour contrast, keyboard navigation,
visible focus states, meaningful labels, and semantic markup.

Do not sacrifice mobile usability for desktop aesthetics.

============================================================
14. SECURITY AND DATA PROTECTION
============================================================

Do not expose secrets or private customer information.

Do not place credentials in source code.

Do not publish actual customer records, phone numbers,
payment details, API credentials, or private conversations.

Use fictional demonstration data for mockups and label
it appropriately when necessary.

Do not claim regulatory compliance or certifications
without verified evidence.

============================================================
15. LOCAL DEVELOPMENT AND DEPLOYMENT RESTRICTIONS
============================================================

This is a local development project.

The website must not be described as live or deployed
unless deployment has actually been completed and verified.

Do not deploy the website without explicit authorisation.

Do not publish the website or connect a production
domain without explicit authorisation.

Do not alter production infrastructure.

Do not execute destructive Git commands.

Do not delete branches, reset project history, or
overwrite user work without explicit permission.

Do not remove existing assets or files simply because
they appear unused. Verify references first.

============================================================
16. REQUIRED WORKFLOW BEFORE IMPLEMENTATION
============================================================

For every substantial task:

STEP 1 — INSPECT
Inspect the relevant pages, components, configuration,
styles, assets, and documentation.

STEP 2 — UNDERSTAND
Understand how the existing implementation works.
Identify reusable components and dependencies.

STEP 3 — VERIFY
Verify product claims and functionality against
the actual repository.

STEP 4 — PLAN
Identify the exact files and components requiring changes.
Avoid unnecessary scope expansion.

STEP 5 — IMPLEMENT
Make focused changes consistent with the existing
architecture and design system.

STEP 6 — VERIFY
Run appropriate checks, including:
- Build.
- Type checking where configured.
- Relevant linting where configured.
- Internal link verification.
- Responsive inspection.
- Browser inspection where available.
- Light and dark theme inspection.

STEP 7 — REPORT
Summarise:
- What changed.
- Files modified.
- Features improved.
- Checks performed.
- Outstanding problems.
- Claims or capabilities requiring confirmation.

Never claim that a check passed unless it was executed.

============================================================
17. CHANGE CONTROL
============================================================

Do not silently make major decisions about:
- Product positioning.
- Pricing.
- Brand identity.
- Application architecture.
- Framework changes.

For routine, reversible improvements within the
approved scope, proceed without unnecessary interruption.

The finished MarkChat website must be:

PRESERVE THE EXISTING VIREX DESIGN IDENTITY.
IMPROVE THE EXISTING MARKCHAT WEBSITE.

- Careers.
- FAQs.

PUBLIC_BRIDGE_API_URL

the environment variable or client exists.

- published

in an older specification.
